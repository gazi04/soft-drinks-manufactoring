## What this is

University PLC course project (master's, *PLC Programming*): a full soft drink production line (blow moulder → syrup/carbonator → filler/capper → labeler → 6-pack packer) controlled by OpenPLC, with a Python plant simulator and a FUXA web HMI/SCADA. Runs natively on Arch Linux with Docker.

## Architecture

Three separate programs form one closed loop over **Modbus TCP**:

- **OpenPLC Runtime v4** (Docker, `ghcr.io/autonomy-logic/openplc-runtime`) — the only component that makes control decisions. Modbus server. PLC programs are written in the OpenPLC Editor v4 (AppImage) and uploaded via port 8443 (Editor v4 hard-codes the port, so each runtime has its own loopback IP: filler `localhost`/127.0.0.1, syrup room 127.0.0.2, labeler 127.0.0.3 – report 6.1); projects live in `plcs/<machine>/` (`plcs/filler/`, `plcs/syrup/`, `plcs/labeler/`). `plc/` on disk is the old throw-away `test-mapping` project (never committed).
- **Python simulator** (`simulator/`, how to run: `simulator/README.md`) — the "factory": reads PLC outputs, simulates physics, writes sensor values back. Complete for the filler (stages 0–9): pure physics (`plant.py` composes conveyors, `machines/filler.py`, `standins.py`; no Modbus/UI, returns sensors + events), `plcs.py` (the only Modbus file), `loop.py` (fixed-rate tick loop), `commands.py` (command queue, the only way to change the world at runtime, applied at tick start), `scenarios.py` (fixed command sequences with time or condition steps), Textual control panel `ui/` (`view.py` pure text builders, `app.py` the screen; controls only put commands on the queue; loop runs as a Textual worker), CLI `uv run simulator [--headless] [--scenario NAME]`. It also writes the HMI animation words %MW70–75 (C1/C2 slot bits, filler pocket state codes; layout in `docs/filler/io-list.md`) and reads `ModeReq` (read only) for the panel header. Never run the `tests/` scripts while the simulator runs (both write the sensors) – enforced by `plant_lock.py` (OS file lock per PLC host:port; a second simulator or sensor-writing test script stops with a message). Decisions that look odd (sub-steps, S7 on C2 slot 1, lazy Modbus client, read-back before write) are explained in `docs/simulator/design-notes.md` – keep them. Syrup room simulator (`docs/simulator/roadmap.md`, section "Syrup room simulator"): `machines/syrup.py` (tank volumes, temperature, CO2 pressure) and `Plant(with_syrup=True)` (the `Product_Available` wire and the buffer drained by the filler) are built; `plcs.SyrupPlc` (shared `PlcLink` base) talks to the syrup PLC and `loop.run(..., syrup_plc=)` drives both PLCs (default of `uv run simulator`; `--filler-only` for the old behavior). Real batch verified on the syrup PLC; the filler fed by the real `Product_Available` verified live (`test_closed_loop_syrup.py` B4, 2026-11-13).
- **FUXA** (`frangoteam/fuxa:1.3.5`, pinned) — operator screens. `hmi/` is mounted as FUXA's `_appdata` (live SQLite DBs + settings, owned by root, git-ignored); the trend history (DAQ, `server/_db`) is on the volume `fuxa-daq`, the Modbus plugin on `fuxa-plugins`; the project is versioned only as `docs/hmi/fuxa-project.json` – export it after every editor change (command above). Generated by `simulator/tests/fuxa_tags.py` (devices/tags, `Machine` per PLC) + `fuxa_views.py` (views, alarms, trend charts, side menu) + `fuxa_shapes.py` (FUXA shape formats); build/test steps and FUXA 1.3.5 findings in `docs/hmi/roadmap.md`. FUXA is an HMI writer (Cmd, ModeReq, setpoints, Man_*): `tests/hmi_guard.py` reminds `hmi.py` and the test scripts not to run while an operator uses it.

Rules that span components:
- Simulator and FUXA **never talk to each other** — everything goes through PLC memory.
- External Modbus clients cannot write `%IX` inputs, so **sensor values go into `%MW` memory words** that the PLC reads as sensors. Verify OpenPLC v4's `%MW` → holding-register offset before fixing addresses (v3: `%MW0` = HR 1024).
- Use **IEC addresses** (`%IX`, `%QX`, `%MW`), not Delta's X/Y/M/D.
- **Ladder Diagram is the primary language**; Structured Text only where ladder is clearly unsuitable.

Running today: `openplc` (filler), `plc-syrup-carb` (volumes `syrup-data`/`syrup-build`) and `plc-labeler` (volumes `labeler-data`/`labeler-build`). Renaming the filler service to `plc-filler` is optional and keeps its addresses.
- Every PLC uses the **same standard register layout** (report 6.2: Booleans as `%MX` coils, numbers as `%MW`; `Alm_CommLost` = `%MX5.3` everywhere; commands, sensors, interface in/out, state, step, alarms, animation slots) so simulator and HMI code is shared.
- Machines never read each other's memory. Bottle flow: each conveyor's full sensor is wired to the **upstream** machine (which stops itself, state Blocked); the downstream machine drives the conveyor motor. Liquid flow: one active-high handshake, `Product_Available` (syrup room → filler). The simulator copies it between PLCs to emulate hardwiring, plus `E_Stop_OK` and a heartbeat bit. Signals from machines that don't exist yet are held at their healthy value by the simulator.
- Simulator: one process, one class per machine plus `Conveyor` objects, one tick loop (~100 ms).
- HMI: one overview screen with slot-based conveyor animation, plus a detail screen per machine.
