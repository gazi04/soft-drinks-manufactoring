## Why the filler first

- Covers both kinds of control: a step sequence (door → rinse → fill → cap → discharge) and an analog value (fill level).
- Has three neighbours (bottles on C1, liquid from the syrup room, C2 to the labeler), so every connection pattern gets tested early.
- Produces the reusable parts for the other four machines: `FB_Motor`, `FB_Valve`, mode/E-stop section, alarm word, standard register layout.

## Order of work and why

1. **Paper first** – I/O list and state diagram. Ladder, simulator and FUXA all depend on the addresses and steps; changing them later means changing three places.
2. **Ladder logic** – the PLC is the brain; simulator and HMI only read/write its registers. It can be tested alone by forcing inputs in the OpenPLC Editor debugger. It is the graded core.
3. **Python simulator** – once the sequence works with forcing (forcing a full cycle by hand gets tedious). First closed loop: PLC opens valve → level rises → PLC closes valve.
4. **FUXA HMI** – last; it only displays and sends commands, and its tag addresses are final by then.

| 2026-10-27 | Stop is acted on only at safe points (end of INDEX, WORK with all jobs done, WAIT_OUTFEED); bottles may stay inside and the machine continues on the next Start. |
| 2026-10-28 | Manual mode: buttons are hold-to-run (jog); switching Manual → Auto goes to IDLE (step 0), then Start. `Stop_Request` latch is cleared when the machine reaches IDLE. |
| 2026-10-28 | **Address layout:** every Boolean signal is its own `%MX` bit (sensors %MX0.x, interface %MX1.x, manual buttons %MX2.x, alarms %MX5.x); numbers stay in `%MW`. Packed `ManualCmd` and `AlarmWord` words dropped. Reason: OpenPLC v4 has a `%MX` segment readable/writable as coils, so ladder needs no bit extraction from words. |
| 2026-10-30 | `FB_Motor` has no seal-in: the sequencer and the HMI hold the request (`Run`), the FB only gates it with `Enable` and counts. Valve open time is measured per opening (TON `ET` at the falling edge), not with a pulse counter: short openings (1–3 s) would lose up to a whole pulse each. |
| 2026-11-01 | **Rung order: a value is computed above every rung that uses it in the same scan.** Station jobs (done bits) sit between the step decode and `Jobs_Done`/transitions, not after the transitions as first planned in `ladder-roadmap.md`. Reason: with the done bits below, a bottle arriving during WORK met a `Jobs_Done` = TRUE left over from the previous scan (empty stations = done) while `Bottles_Present` was already TRUE, so the machine indexed after one scan without doing the job. |
| 2026-11-01 | Setpoints stay `INT` in ms at their `%MW` addresses; conversion to `TIME` is done in the rung with `TO_TIME`. Interface variables (addresses in `io-list.md`) never change type to suit a block; mismatches are solved with conversion blocks and internal helper variables. |
| 2026-11-02 | **Outputs: one writer per `%QX`.** Each output gets a request rung (`Req_…` = Auto branch OR Manual branch) and one FB rung (`Run`/`Open` = request, `Enable` = `Master_Enable`, `Out` → output). `Ilk_Index` is built from the requests, not from the outputs: the outputs are written further down, so it would see the previous scan and valve + belt could be ON together for one scan. Auto branch of `IndexMotor` and the door come in stage 6. |
| 2026-10-27 | The single `openplc` service in `docker-compose.yml` is used as the filler PLC for now; split into five services when the second machine starts. |
| 2026-11-02 | **Simulator control panel in Textual** (terminal UI), not pygame: built-in inputs, switches and a coloured scrolling log; graphics are FUXA's job. The panel changes only the physical world and the wiring (supply, jams, E-stop, product); it never writes `Cmd`, mode or setpoints, so it does not become a second HMI. |
| 2026-11-02 | Simulator structure: physics classes are pure Python (no Modbus, no UI) and return sensors + events; the UI sends commands through a queue applied at the start of a tick; `--headless` runs without the panel (Docker). Bottles are objects that carry their state (ml, rinsed, capped), so the simulator can audit the PLC. |
| 2026-11-02 | The `simulator/tests/` scripts and the simulator both write S2–S8: never run them at the same time (two writers). |

| 2026-11-02 | `plcs.py` link problems analysed in the pymodbus 3.16.1 source and fixed properly (4 improve-cycles). Root causes: (P1) the async client calls `asyncio.get_running_loop()` in its constructor, so it is bound to the loop that exists then; (P2) `ModbusBaseClient.execute()` is a *sync* function that raises `ConnectionException` while the request is created when the transport is gone; (P3, found in the analysis) TCP "connected" is no proof the PLC answers (Docker's port proxy accepts during a runtime restart); (P4) an error *reply* means the PLC answered – reconnecting would hide a config error such as `mx_bits` = 0. Fixes: lazy client, a fresh `AsyncModbusTcpClient` per connection made inside `ensure_connected()` (P1, no stale state after a restart); every request = `_live_client()` link check, then create + await with no `await` in between, so the sync raise cannot happen – asyncio switches tasks only at an `await` (P2; replaces the lambda patch, which also misreported programming errors such as `ParameterException` as link errors); `link_ok` = last request answered (P3); `PlcReplyError(PlcCommError)` keeps the link (P4). New `tests/unit/test_plcs_link.py` with an in-process pymodbus server (no PLC/Docker): request without connection, error reply keeps the link, server shut down → `PlcCommError`, server back → reconnect. Mutation check: with the link check removed, the test fails with exactly the original `ConnectionException`. Note: pymodbus 3.16 data blocks count from 1 (`ModbusSequentialDataBlock(1, …)` = address 0). Unit tests 76/76, `test_link.py` 5/5. |
| 2026-11-02 | Simulator state analysed (jitter experiments, real link timing: 4 reads ≈ 7 ms, naive loop period 102–110 ms). All unit tests used exactly dt = 0.1 s; with real, uneven ticks the physics produced false audit warnings and even let unprocessed bottles leave. Three mechanisms found and fixed: (1) **queue start from rest** – a bottle standing behind the door now needs a full slot step after the front one is taken (`Conveyor.take_at_exit` resets the step timer when the next slot is occupied); before, it could reach the door at once and a correct 0.5 s door pulse admitted two bottles (fixing it with a longer pass time only works up to dt ≈ 0.13 s); (2) **sub-steps** – `Plant.step` splits a late tick into steps ≤ 0.1 s, otherwise "next bottle arrives" and "door timer counts the whole dt" happened at once (capping dt instead was tried and rejected: it shifts simulator time against the PLC's wall-clock timers → false "not rinsed"); (3) **pulse sensors kept for one write** – S6/S8 are written ON if they were ON in any sub-step of the tick (report 7.3 rule); a lost S8 edge let the belt run on and bottles skip the cap station, a lost S6 would undercount `GoodCount`; presence sensors S3–S5 are deliberately not stretched. Plus `STATION_WINDOW` = 40 % of a pitch for S3–S5 (separate from the 15 % cam), and a "slow tick" SIM warning above 0.3 s so a warning caused by the simulator is never blamed on the PLC. Result (10 runs × 600 s): jitter 0.08–0.2 s and 0.4 s stalls → 0 bottle warnings; longer stalls still fail but always together with "slow tick". Every fix has a unit test that fails without it (mutation check).
